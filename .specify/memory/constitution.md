# Design Studio Constitution

The agentic design team ships product work from PRD/BRD to live site using **only** the
Lumen design system. These principles bind every `/speckit-*` artifact (spec, plan,
tasks) and every agent in the studio (Nova, Ivo, Mika, Ren, Sol, Priya, Tess).

## Core Principles

### I. Lumen Only (NON-NEGOTIABLE)
Every visual decision resolves to Lumen.
- Figma: every node is an instance from the Lumen library (`Lumen_Desing System`,
  file `vCPe93hNKDWWcpu49Vo0kU`) or bound to a Lumen variable (`☀️ Mode`, `🚀 Themes`,
  `💨 Tailwind`). No detached instances, no local styles, no raw hex, no eyeballed spacing.
- Code: colours, spacing, radii, type, shadows come from the token manifest
  (`tokens/dist/manifest.json`, generated by `npm run tokens:sync`). No arbitrary
  Tailwind values (`bg-[#…]`, `p-[13px]`), no raw `#hex` / `rgb()` / `hsl()`, no
  ad-hoc `font-family`. `npm run tokens:lint <dir>` MUST pass before any approval.
- If Lumen lacks something, the work STOPS and a **component brief** is raised. Agents
  never improvise a one-off to unblock a feature.

### II. Tokens Flow One Way: Figma → JSON → CSS
- Source of truth is the Figma variable collections, exported by the "Lumen token sync"
  plugin into `tokens/figma/*.json` exactly as emitted (no renaming).
- `scripts/sync-tokens.mjs` generates `tokens/dist/**`. Generated files are never
  hand-edited. A token change is a Figma change first, then a re-sync.
- Brands render via `[data-brand='<brand>']` (+ `.dark`). The pretend live site runs
  brand `betonline` unless the brief says otherwise.

### III. Components Before Features
- A feature may only import components that are **approved in Storybook**.
- A new or changed component ships as: Figma component set → React component whose
  props mirror the Figma variant properties → stories per variant → Code Connect
  mapping → human approval in Storybook. Only then can a feature use it.

### IV. Spec-Driven, Gate-Driven
- Every brief starts from a PRD/BRD and becomes `specs/<slug>/spec.md`
  (`/speckit-specify` + `/speckit-clarify`), then `plan.md` and `tasks.md`.
- The studio pipeline is the gate list; each ✋ is a human approval in chat:
  spec ✋ → Lumen audit ✋ → Figma ✋ → prototype URL ✋ → Storybook ✋ (components) /
  live-site preview ✋ (features) → QA ✋ → launch.
- Nothing merges to the live site without QA sign-off against the spec's acceptance
  criteria plus visual diff vs Figma, token lint, a11y (contrast, focus, labels) and
  the Lumen breakpoints (xs 375 · sm 390 · md 1200 · lg 1440 · xl 1728 · 2xl 1920).

### V. Ask a Human, Don't Guess
- An agent sent back twice on the same stage, or unable to map a brief onto Lumen,
  MUST escalate: post a `needs a human` message naming the reviewers in
  `PUBLIC_HUMAN_REVIEWERS`, block its tasks, and wait for a reference
  (`/reference <url> <note>` or the brief page). Escalations are never silent.
- Agents may ask clarifying questions in the brief's channel at any stage; unanswered
  questions block work rather than being assumed.

## Technology & Targets
- Studio app: Astro 6 + React 19 + Pixi 8 + Tailwind 4 (`src/`).
- Prototypes: static builds published under `PUBLIC_PROTOTYPE_BASE_URL/<slug>/`,
  built from Lumen tokens + approved components only.
- Live site: `apps/live-site` (Next.js 14 + shadcn/Radix). Features land as a branch
  `feature/<slug>` + PR + preview deploy, merged only after sign-off.
- Storybook: `PUBLIC_STORYBOOK_URL`; every approved component has a story and a
  Figma link.
- Secrets live only in `.env` (never `PUBLIC_` for server keys, never committed).

## Development Workflow
1. `/speckit-constitution` (this file) — amend only via PR with a version bump.
2. Per brief: `/speckit-specify` → `/speckit-clarify` → `/speckit-plan` →
   `/speckit-checklist` → `/speckit-tasks` → `/speckit-analyze` →
   `/speckit-implement` → `/speckit-converge`.
3. Plans MUST list the Lumen components/tokens they rely on (from the audit) and
   MUST NOT introduce new UI primitives outside Principle III.
4. Tasks MUST include: token lint, Storybook stories (components), Figma diff, and
   the approval checkpoints from Principle IV as explicit, blocking items.

## Governance
This constitution supersedes any other practice, prompt or template in the repo.
Reviews verify compliance with Principles I–V before approving. Complexity or any
deviation must be justified in the plan's Complexity Tracking table and approved by a
human reviewer. Runtime guidance for agents lives in `.cursor/skills/speckit-*` and
`src/lib/studio/pipeline.ts` (the gate list).
